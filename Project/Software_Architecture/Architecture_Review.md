## Problems found and how they were fixed

1. **Architecture_Consistency_Check.md, section C (owner: Member 2).** The sentence after the table says that in every diagram the actor's first message goes to a control object (ItemSearch, MatchingService, DisputeCase). This is not correct for UC-14: there the first message (viewPendingClaims) goes to CampusSecurityOfficer, and DisputeCase is an «entity» class in the Lab 5 class diagram, not a control class. The table row for UC-14 in the same section is correct. Fix sent to Member 2: in UC-03 and UC-09 the actor's first message goes to the control object (ItemSearch, MatchingService); in UC-14 the officer works through CampusSecurityOfficer and DisputeCase, all inside CO5. In the architecture this is the Web Interface calling ISearchService, IMatchingService, IClaimService and IDisputeService.
2. **Architecture_Consistency_Check.md, section A (owner: Member 2).** The NFR-10 sentence says the matching logic is kept separate from Report Management. NFR-10 also names the notification features, which share CO4 with matching. Suggested addition: "Matching and Notification share CO4 but stay separate classes; see Architectural_Style_Selection.md, section 6."
3. **Diagram (cosmetic, no fix needed).** The socket line from Account Management (CO1) to IDataAccess has one diagonal segment. It is still joined correctly and does not change the architecture.
